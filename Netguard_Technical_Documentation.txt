# NetGuard Technical Documentation

## SECTION 1
PROJECT IDENTIFICATION

Project Title: NetGuard

System Name: NetGuard SOC Dashboard and Network Threat Monitor

Type of software: Web-based security operations center prototype and network intrusion detection system

Industry: Cybersecurity, network security, information security, threat monitoring, incident response

Purpose:
NetGuard is designed to detect, log, visualize, and alert on suspicious network activity. It provides a browser-based dashboard to view threats and manages a backend monitor that captures network traffic, detects threat behavior, records incidents, and optionally sends alerts.

Main problem solved:
The system addresses the need for real-time detection and tracking of network-based attack patterns such as port scanning, brute-force attempts, distributed denial-of-service (DDoS) behavior, suspicious port usage, anomalous packet sizes, and rapid traffic from remote hosts.

Target users:
- Security operations center analysts
- Network administrators
- Cybersecurity students and researchers
- Internal IT teams responsible for threat detection and incident response

Stakeholders:
- System developers and maintainers
- Security analysts and operators
- Network engineers
- Academic supervisors and evaluators
- End users running the dashboard for network monitoring

Scope:
NetGuard covers local network traffic monitoring, threat detection with predefined heuristics, persistent logging of detected threats to a PostgreSQL database, browser-based threat visualization, and a manual simulator interface. It does not implement advanced authentication, role-based access control, multi-tenant architecture, or production-grade security hardening.

Objectives:
- Provide a lightweight dashboard to observe detected threats.
- Capture and analyze incoming network traffic using raw sockets or fallback to psutil.
- Detect multiple threat categories using heuristic rules.
- Persist threat events to a database.
- Support start, stop, and clear operations for simulation of threat generation.
- Send email alerts when threats are detected if SMTP configuration is provided.

Core features:
- Threat logging to PostgreSQL.
- Live web dashboard with threat table and bar chart.
- Simulated threat injection engine.
- Real network packet monitoring using raw sockets.
- Fallback monitoring using psutil to support non-admin operation.
- Alert notification via email.
- Threat statistics aggregation.
- Manual threat simulation controls.

Business value:
- Enables fast detection and tracking of suspicious traffic.
- Helps build situational awareness for network security teams.
- Supports proof-of-concept cybersecurity demonstrations.
- Provides a reusable academic platform for network security research and coursework.

Real-world application:
- Small enterprise network monitoring.
- Security operations or SOC training environments.
- Academic research on heuristic-based intrusion detection.
- Proof-of-concept demonstrations for detecting port scanning, brute force, and anomaly attacks.

## SECTION 2
HIGH LEVEL OVERVIEW

Entire software architecture:
NetGuard consists of a monolithic Python application with two distinct runtime entry points: `app.py` for the web dashboard and threat simulation, and `main.py` for packet-level monitoring and threat detection. Shared backend logic lives in `database.py` for persistence and `alert.py` for notifications.

System overview:
- The web module (`app.py`) exposes a Flask application that renders a dashboard and performs simulator lifecycle operations.
- The monitor module (`main.py`) executes on the host and either listens on a raw socket for TCP traffic or uses `psutil` to inspect established connections.
- Database operations are centralized in `database.py`, which initializes a PostgreSQL table and provides CRUD functions for threat events.
- Alerting is implemented in `alert.py` and sends email notifications via SMTP if credentials are configured.
- The web UI uses server-side Jinja2 templates to render threat data and Chart.js for visualization.

Workflow:
1. On startup, the system initializes the database schema.
2. For monitoring, the backend starts traffic capture and detection either through raw sockets or `psutil`.
3. When suspicious activity matches detection heuristics, a threat event is logged and an alert is optionally dispatched.
4. The web interface retrieves aggregated threat data and renders it to the user.
5. The user can start or stop the simulated threat generator and clear stored threats.

User journey:
- Navigate to the dashboard at `/`.
- Review the threat table and summary cards.
- Start the simulator if it is not already running.
- Stop the simulator or clear threats as needed.
- Observe the threat distribution chart update with new threats.

Data flow:
- Threat detection logic in `main.py` or simulated threat insertion in `app.py` writes to the `threats` table via `database.py`.
- The web request handler in `app.py` reads the threat event list and aggregated counts from the database, packages them into template context, and returns HTML.
- Frontend JavaScript renders the aggregated data chart using Chart.js.
- Environment variables configure the database connection and alert email credentials.

Request lifecycle:
- HTTP GET `/` triggers `app.index()`, which calls `get_threats()` and `get_threat_stats()` and renders `templates/index.html`.
- HTTP POST `/start` triggers `app.start()`, starting the simulator thread, then redirects to `/`.
- HTTP POST `/stop` triggers `app.stop()`, stopping the simulator, then redirects to `/`.
- HTTP POST `/clear` triggers `app.clear()`, deletes all threat records, then redirects.
- An unadvertised HTTP POST `/ng-admin-toggle-7x` toggles the simulator state and redirects.

Overall execution flow:
- On application startup, `init_db()` is called from both `app.py` and `main.py`; this creates the PostgreSQL `threats` table if absent.
- `app.py` starts as a Flask server listening on `0.0.0.0:5000` or the configured `PORT`.
- The simulator thread in `app.py`, when started, generates threats with random types and random source IPs at random intervals between 4 and 10 seconds.
- `main.py` attempts raw packet capture; if `PermissionError` or other exceptions occur, it falls back to `psutil` network connections.
- Threat heuristics evaluate network behavior within time windows and thresholds.
- Detected threat events are persisted and optionally trigger email alerts.

## SECTION 9
BUSINESS LOGIC

Feature: Threat simulation
- Purpose: Enable demonstration of how detected threats appear in the dashboard without requiring real network traffic.
- Logic: `threat_simulator()` runs in a background thread while `simulator_running` is `True`.
- Execution flow:
  1. `start_simulator()` checks `simulator_running`; if false, sets it true.
  2. Spawns a daemon thread executing `threat_simulator()`.
  3. The thread chooses a random threat type and random IP, formats the timestamp, inserts it into the database, and sleeps 4–10 seconds.
  4. `stop_simulator()` sets `simulator_running` false to exit the loop.
- Files involved: `app.py`, `database.py`, `templates/index.html`.
- Functions involved: `start_simulator()`, `stop_simulator()`, `threat_simulator()`, `random_ip()`, `insert_threat()`.
- Database interaction: Inserts records into `threats`.
- External interaction: None.
- Edge cases:
  - If the simulator thread fails, no recovery mechanism exists.
  - `simulator_running` is global; concurrent modifications are not synchronized with locks.

Feature: Threat logging and persistence
- Purpose: Save detected events for reporting and historical analysis.
- Logic: Threat events are inserted with raw SQL statements.
- Execution flow:
  1. `init_db()` creates the table if needed.
  2. `insert_threat()` inserts a new row.
  3. `get_threats()` returns rows ordered by descending `id`.
  4. `get_threat_stats()` groups counts by threat type.
  5. `clear_threats()` deletes all rows.
- Files involved: `database.py`, `app.py`, `main.py`.
- Functions involved: `init_db()`, `get_conn()`, `insert_threat()`, `get_threats()`, `get_threat_stats()`, `clear_threats()`.
- Database interaction: PostgreSQL statements executed via `psycopg2`.
- External interaction: None beyond the database engine.
- Edge cases:
  - Failure to connect to the database causes errors.
  - Race conditions if parallel writes occur, though PostgreSQL handles concurrent inserts.

Feature: Email alerting
- Purpose: Notify administrators when suspicious events are detected.
- Logic: Compose a simple text email and send via SMTP.
- Execution flow:
  1. `send_alert()` reads `ALERT_SENDER`, `ALERT_PASSWORD`, and `ALERT_RECEIVER` from environment.
  2. If any value is missing, it logs alert text to console and returns.
  3. Otherwise, it creates a MIME text message and sends it through Gmail SMTP SSL on port 465.
- Files involved: `alert.py`, `main.py`.
- Functions involved: `send_alert()`.
- Database interaction: None.
- External interaction: SMTP service at `smtp.gmail.com`.
- Edge cases:
  - Missing environment variables disable email alerts.
  - Any SMTP exception is printed but ignored.
  - There is no retry logic.

Feature: Raw socket packet capture
- Purpose: Monitor inbound TCP traffic directly from the network stack.
- Logic: Use a raw socket and parse IP and TCP headers to extract source/destination addresses and ports.
- Execution flow:
  1. `raw_socket_monitor()` opens a raw IPv4 TCP socket bound to `LOCAL_IP`.
  2. It sets `IP_HDRINCL` to include IP headers.
  3. It receives raw packet data and calls `parse_packet()`.
  4. If the packet destination is not local, it continues.
  5. If the source IP is blacklisted, it logs a blocked write and continues.
  6. It parses TCP ports, then runs threat detectors.
- Files involved: `main.py`.
- Functions involved: `raw_socket_monitor()`, `parse_packet()`, `parse_tcp()`, detection functions.
- Database interaction: Via `log_threat()` when a threat is detected.
- External interaction: Operating system network stack.
- Edge cases:
  - PermissionError triggers fallback to psutil.
  - Exceptions during packet parsing are caught and ignored.

Feature: psutil connection monitoring fallback
- Purpose: Allow threat monitoring without administrator privileges.
- Logic: Inspect established TCP connections and infer suspicious activity from connection metadata.
- Execution flow:
  1. `psutil_monitor()` fetches network connections every 3 seconds.
  2. It builds a map of remote IP addresses and remote ports.
  3. It applies suspicious port detection and brute-force heuristics.
  4. It detects port scans by counting unique remote ports per source.
  5. It detects rapid traffic by counting connection instances from the same IP.
- Files involved: `main.py`.
- Functions involved: `psutil_monitor()`, `log_threat()`, inline detection logic.
- Database interaction: `insert_threat()` when threats are detected.
- External interaction: OS network APIs via psutil.
- Edge cases:
  - `psutil.net_connections()` may return incomplete or privileged-only data.
  - Non-blocking exception handling logs and continues.

Feature: Threat detection heuristics
- Purpose: Identify suspicious traffic patterns.
- Logic: Maintain in-memory state for each source IP and evaluate thresholds.
- Detectors:
  - Port scan: `PORT_SCAN_THRESHOLD=5` unique ports scanned within `TIME_WINDOW=10` seconds.
  - Brute force: 5 connection attempts to authentication-related ports within 60 seconds.
  - DDoS: More than 30 packets within 5 seconds from a single IP.
  - Suspicious port: Any connection to risky ports `[23, 445, 3389, 4444, 8080]`.
  - Anomaly: Packet size more than 3 times the average of previous sizes.
  - Rapid traffic: More than 10 established connections from a remote IP in the psutil view.
- Files involved: `main.py`.
- Functions involved: `detect_port_scan()`, `detect_bruteforce()`, `detect_flood()`, `detect_suspicious_port()`, `detect_anomaly()`, inline logic in `psutil_monitor()`.
- Database interaction: `log_threat()` on detection.
- External interaction: None.
- Edge cases:
  - Attackers can evade thresholds by spacing traffic.
  - False positives are possible for legitimate high-volume connections.
  - `cooldown_ok()` suppresses repeated alerts within `ALERT_COOLDOWN=30` seconds per source IP.

- `detect_port_scan(src_ip, dst_port)`: Tracks unique destination ports for a source IP in the last 10 seconds. Signals a port scan and blacklists the IP when the threshold is reached.

- `psutil_monitor()`: Polls `psutil.net_connections(kind='inet')`.

## SECTION 13
ALGORITHMS

Identify all algorithms:
- Random IP generation.
- Random threat selection.
- Port scan detection.
- Brute-force detection.
- DDoS detection via traffic rate.
- Suspicious port detection.
- Packet anomaly detection.
- Raw packet parsing.
- Fallback connection aggregation.

Explain:

Algorithm: Random IP generation
- Purpose: Generate pseudo-random source IP addresses for simulator events.
- Logic: Concatenate four random octets, with first and last octets selected from 1-254, middle octets from 0-254.
- Pseudo code:
  - return f"{rand(1,254)}.{rand(0,254)}.{rand(0,254)}.{rand(1,254)}"
- Complexity: O(1).
- Optimization: None needed.

Algorithm: Threat simulation
- Purpose: Periodically insert synthetic threats.
- Logic: Loop while running, choose a random threat from a list, generate random IP, insert event, sleep random duration.
- Complexity: O(1) per event.
- Optimization: Minimal; uses random intervals.

Algorithm: Raw packet parsing
- Purpose: Extract IP and TCP header fields from raw packet bytes.
- Logic: Unpack the first 20 bytes for IP header and bytes 20-40 for TCP header.
- Pseudo code:
  - iph = struct.unpack('!BBHHHBBH4s4s', ip_header)
  - src_ip = inet_ntoa(iph[8])
  - dst_ip = inet_ntoa(iph[9])
  - protocol = iph[6]
  - size = len(data)
  - return src_ip, dst_ip, protocol, size
- Complexity: O(1) per packet.
- Optimization: No additional optimization.

Algorithm: Port scan detection
- Purpose: Detect if a source IP contacts many distinct destination ports quickly.
- Logic:
  1. Append `(dst_port, now)` to `suspicious_ips[src_ip]`.
  2. Keep only entries within the last `TIME_WINDOW` seconds.
  3. Count distinct ports.
  4. If count >= `PORT_SCAN_THRESHOLD` and cooldown allows, log threat and blacklist IP.
- Pseudo code:
  - suspicious_ips[src_ip].append((dst_port, now))
  - filter old entries older than TIME_WINDOW
  - ports = set(port for port,t in suspicious_ips[src_ip])
  - if len(ports) >= threshold and cooldown_ok(src_ip): log_threat("Port Scan", src_ip); blacklist.add(src_ip); clear list
- Complexity: O(n) where n is entries per IP.
- Optimization: list filtering and set construction; manageable due to small window.

Algorithm: Brute-force detection
- Purpose: Detect repeated attempts on sensitive ports.
- Logic:
  1. If `dst_port` is in authentication-related ports, append timestamp.
  2. Keep only timestamps within 60 seconds.
  3. If count >= 5 and cooldown allows, log threat.
- Pseudo code:
  - if dst_port in [22,21,80,443,3389]: login_attempts[src_ip].append(now)
  - filter entries older than 60 seconds
  - if len(login_attempts[src_ip]) >= 5 and cooldown_ok(src_ip): log_threat("Brute Force", src_ip); clear list
- Complexity: O(m) with m attempts for IP.
- Optimization: uses time-based sliding window.

Algorithm: DDoS detection (flood)
- Purpose: Detect high frequency packet bursts from an IP.
- Logic:
  1. Append timestamp to `traffic_count[src_ip]`.
  2. Keep only entries within 5 seconds.
  3. If count > 30 and cooldown allows, log DDoS.
- Pseudo code:
  - traffic_count[src_ip].append(now)
  - filter timestamps older than 5 seconds
  - if len(traffic_count[src_ip]) > 30 and cooldown_ok(src_ip): log_threat("DDoS", src_ip)
- Complexity: O(k) for packet timestamps.
- Optimization: sliding time window.

Algorithm: Suspicious port detection
- Purpose: Flag any connection to a set of risky ports.
- Logic: If `dst_port` is in `RISKY_PORTS` and cooldown allows, log threat.
- Pseudo code:
  - if dst_port in risky_ports and cooldown_ok(src_ip): log_threat("Suspicious Port", src_ip)
- Complexity: O(1).
- Optimization: constant-time membership check.

Algorithm: Packet anomaly detection
- Purpose: Detect packet sizes that deviate from recent average.
- Logic:
  1. Append packet size to `packet_sizes[src_ip]`.
  2. When more than 10 sizes are collected, calculate average.
  3. If current size > average * 3 and cooldown allows, log anomaly.
  4. Reset packet sizes list.
- Pseudo code:
  - packet_sizes[src_ip].append(size)
  - if len(packet_sizes[src_ip]) > 10: avg = sum(list)/len(list)
  - if size > avg*3 and cooldown_ok(src_ip): log_threat("Anomaly", src_ip)
  - packet_sizes[src_ip] = []
- Complexity: O(n) for average calculation when threshold reached.
- Optimization: resets after evaluation.

Algorithm: psutil-based port scan detection
- Purpose: Detect scanning based on remote ports in established connections.
- Logic:
  1. Build `ip_ports` mapping remote IP to a set of remote ports.
  2. After iterating connections, if a source has >= threshold unique ports and cooldown allows, log port scan.
- Complexity: O(c) where c is number of connections.
- Optimization: uses set membership to count unique ports.

Algorithm: Rapid traffic detection in psutil fallback
- Purpose: Identify sources with many established connections.
- Logic: Count occurrences of each remote IP in current connection list; if > 10 and cooldown allows, log rapid traffic.
- Complexity: O(c^2) in current implementation because `all_ips.count(ip)` is repeated for each unique IP.
- Optimization note: This can be optimized with a dictionary count, but current code uses list counting.

## SECTION 23
DESIGN DECISIONS

Why important architectural decisions were made:
- Monolithic Python application: simplifies development and deployment for a small project.
- Flask for dashboard: provides a lightweight web layer without heavy frontend frameworks.
- PostgreSQL with `psycopg2`: uses a production-capable relational database instead of local file storage to demonstrate serious persistence.
- Raw sockets with `psutil` fallback: supports both privileged and non-privileged network monitoring environments.
- Environment variable configuration: enables deployment with secret management and avoids hardcoding credentials.
- Gunicorn in `render.yaml`: standard deployment pattern for Flask apps.
- Single-table schema: keeps data management simple for a proof-of-concept threat log.
- Client-side auto-refresh: reduces the need for WebSockets and simplifies live updates.

Explain every dependency:

- psutil is imported in `main.py` and used when raw socket mode fails.

## SECTION 27
PERFORMANCE

Identify:
- No caching layer.
- Database connections are opened and closed for each operation.
- Auto-refresh every 3 seconds can generate frequent server load.

Optimization:
- Use connection pooling for PostgreSQL.
- Replace list `.count()` in `psutil_monitor()` with dictionary counts.
- Replace string timestamp storage with explicit timestamp type.
- Add caching for repeated dashboard stats queries if scale grows.

Bottlenecks:
- `psutil_monitor()` uses potentially expensive connection inspection and repeated list counting.
- Concurrent Gunicorn workers will each have separate simulator state.
- Frequent dashboard refresh with large result sets could slow response.

Memory usage:
- In-memory threat tracking maps store data for every monitored source IP during runtime.
- These maps are reset by cooldowns and detection functions but can grow if many unique IPs connect.

Database optimization:
- Single table with no indexes besides primary key.
- Aggregation query `GROUP BY threat_type` is acceptable for small datasets.
- For larger datasets, an index on `threat_type` or a normalized threat type table may be beneficial.
